# Community Webtoon Agent Kit

한국 온라인 커뮤니티의 글·댓글·밈·기사·논문을 소재로, **사람의 의도를 AI 작가·편집자·이미지 모델에게 이어주며 세로형 정보·개그 웹툰을 만드는 공개 제작 키트**(`Q0916/community-webtoon-agent-kit`)입니다.

만들고 싶은 이야기를 함께 정리하고, 전편과 장면·컷을 퇴고하고, 이미지 후보를 뽑아 고른 뒤 세로 스크롤 원고로 조립해 완성하는 과정에 쓰는 스킬·양식·검증 스크립트를 담았습니다. 사용자는 원안과 취향, 각색 방향과 최종 선택을 맡고, 에이전트들은 그 의도를 각자의 역할에 맞춰 구체화합니다.

## 왜 이 방식으로 만드는가

LLM과 길게 작업하다 보면 같은 모델이어도 다음 단계의 작업자가 앞선 대화를 겪지 못한 사람처럼 행동할 때가 있습니다. ‘대사는 짧게’, ‘배경은 단순하게’ 같은 결론만 넘기면 왜 그런 판단을 내렸는지 맥락이 사라져, 살려야 할 말맛이나 꼭 필요한 연출까지 잘라내기 쉽습니다.

그래서 이 키트는 <strong>무엇을 만들지와 함께 왜 그렇게 만들려는지(WHY)</strong>를 실제 의뢰 본문에 끝까지 이어줍니다. 처음 포착한 웃음 포인트, 독자가 따라갈 감정 순서, 비유를 고른 이유, 앞선 교정 경위, 다음 작성자가 새로 판단할 여지를 생략하지 않고 전달합니다.

현재 주력 제작 흐름은 다음과 같습니다.

1. **작품과 의도 이해**: 원문 소재에서 사실, 커뮤니티 분위기, 창작 MSG, 사용 금지 요소를 가르고 작품의 핵심 재미를 합의합니다.
2. **전편 → 장면 → 컷 순서의 작법 퇴고**: 처음부터 컷을 쪼개지 않고, 전편의 감정·인과·보상이 제대로 서 있는지 먼저 본 뒤 장면 연결을 다듬고 마지막에 컷을 설계합니다. 장면 이해에 필요한 발화자·상대·반응·핵심 볼거리는 살리고, 불필요한 구경꾼·반복 배경·연속성 부담을 줄입니다. ([작법 퇴고 안내](docs/CRAFT_REVIEW.md))
3. **맥락과 WHY를 담은 실제 입력 조립**: 전체 이야기 흐름, 현재 구간, 앞뒤 상태, 정확한 대사와 화자, 소품의 서사적 이유, 폰 표시 폭 기준의 가독성 목적(글자·대비·풍선 공간)을 입력 본문에 담습니다. 작화 묘사에는 화면에 실제로 보일 면과 글자만 적습니다.
4. **분리 가능한 1-2컷 시트 후보 생성과 사용자 선택**: 승인된 장수·비용 범위 안에서 단위 시간당 사람이 고를 만한 후보를 충분히 확보하고, 사용자가 직접 후보를 고릅니다. 생성 시트 안의 배치와 최종 세로 스크롤 배치는 서로 다른 단계로 다룹니다. ([컷 기반 제작과 세로 편집](docs/CUT_BASED_PRODUCTION.md))
5. **컷별 크기·정렬·간격을 정한 세로 편집**: 선택한 시트에서 컷을 분리한 뒤, 앞 컷 아래 흰 여백과 다음 컷 위 흰 여백을 먼저 재고 목표 거리에서 부족한 간격만 더합니다. 응답·반응·공개·침묵·진짜 장면 전환을 구별해 세로 호흡을 만듭니다. ([컷 배치 퇴고](docs/PANEL_LAYOUT_REVISION.md), [호흡·간격](docs/PANELING_AND_PACING.md))
6. **전체 보기본 보관 및 게시용 무손실 분할**: 완성된 전체 보기본은 따로 보관하고, 커뮤니티 업로드용 파일은 안전한 흰 여백에서만 원본 폭·픽셀·행·글자·기존 여백을 그대로 유지해 분할한 뒤 번호순으로 전달합니다. ([업로드와 무손실 분할](docs/UPLOAD_DELIVERY.md))

특정 작품에서 쓴 `1024x1536` 해상도, 컷 수, 고정 중앙 흰띠 폭, 인물 수 상한, 의상, 배율과 간격 수치를 모든 작품의 고정 규칙으로 복사하지 않습니다. 이전 세대의 **전체 페이지 프로필**(한 페이지 안에 2-4블록과 여백 예산을 함께 생성하는 방식)과 최신 **1-2컷 시트 + 세로 편집 프로필**은 목적에 따라 구별해 사용하며, 기존 전체 페이지 양식과 채택 입력은 해당 작품 재현 범위로 보존합니다.

## 공개 키트의 범위와 별도 준비 도구

이 저장소는 Python 3.10+ 표준 라이브러리만으로 동작하는 5개 스크립트를 제공합니다.

- `harness/scripts/init_project.py`: 새 작품 작업 폴더와 기본 템플릿 초기화
- `harness/scripts/validate_project.py`: `page_id` 기반 콘티·텍스트·캐스트·레퍼런스·프롬프트 잠금 및 Gemini 원출력/사람 승인 기록 검증
- `harness/scripts/provider_instruction_integrity.py`: 승인된 생성 지침 원문과 허용된 수정 범위의 무결성 확인
- `harness/scripts/freeze_completion.py`: 완성본·승인 원본·사용 소재 복사와 SHA-256 해시 매니페스트 동결
- `harness/scripts/verify_repository.py`: 필수 파일·미디어 제외·개인 경로 및 토큰 패턴·스킬 메타데이터 검사

공개 키트 자체에는 **실제 이미지 생성 runner, 누적 receipt 저장소, 컷 시트 분리·세로 재배치 도구, 업로드용 무손실 분할 및 높이·용량 자동 검사 도구가 포함되어 있지 않습니다.**

- 실제 이미지 생성은 별도로 설치하는 [**ima2-gen**](https://github.com/lidge-jun/ima2-gen)(Node.js 20+ 필요)을 기본 실행기로 사용합니다.
- 공개 `validate_project.py`는 기존 `page_id` 기반 잠금 양식을 검증하며, 새로 추가된 1-2컷 시트 프로필이나 세로 편집 결과를 자동으로 검증하지 않습니다.
- 공개 `freeze_completion.py`는 파일 복사와 SHA-256 해시 검증 도구이며, 업로드용 세로 길이·파일 용량 검사나 무손실 분할·재결합 검사는 사용자가 별도 편집·검사 스크립트나 작업 환경을 준비해 수행합니다.

생성은 **대량 병렬 샘플링과 사람의 선별**로 운영합니다. 승인된 장수·비용 안에서 후보 풀·wave 크기·동시 실행 수를 구별해 단위 시간당 고를 만한 후보를 확보하고, 개별 실패율만으로 소규모 모드를 자동 선택하지 않습니다. 사용자의 수량·재시도 제한을 우선하며, 성공 원본과 요청 식별을 보존하고 늦은 성공을 회수합니다. 자세한 기준은 [실행 원칙과 용어](docs/PROVIDER_ADAPTER.md#대량-병렬-후보-탐색)를 참고하세요.

## 누가 무엇을 맡는가

| 주체 | 역할과 전문 판단 |
|---|---|
| **User / Director** | 원작자·총괄 크리에이티브 디렉터. 기획·원안·각색 방향, 작품의 의미와 취향, 생성 범위 승인, 최종 시각 선택을 결정합니다. |
| **AGY / Gemini** | 위임받은 집필·콘티 구성·문장 편집 담당. 거친 뼈대의 빈칸 채우기뿐 아니라 자유 집필, 완성된 원고의 퇴고와 문장 정리까지 사용자의 실제 위임 범위에 따라 수행합니다. |
| **Codex / Producer** | 사실·연속성 확인과 제작 실행 담당. 원안 대조, 검토 의견 정리, 독자와 매체에 맞는 전달, 입력 조립·검증 실행·세로 편집·보관 진행을 맡습니다. |
| **검증 하네스와 실행기** | 채택된 텍스트·캐스트·참조·입력 결합을 검사하고 실제 후보를 생성합니다. 창작 판단과 시각 선택은 사람과 작가·편집자가 맡습니다. |

자세한 협업 방식은 [역할의 이유와 판단 사례](docs/CREATIVE_ROLES.md)와 [창작 맥락을 이어주는 서술](docs/CREATIVE_CONTINUITY.md)에 정리되어 있습니다. AGY 초안은 원문 그대로 먼저 보존해 사용자에게 전달하고, 이후 사용자의 위임에 따라 공동 검토(`adopt / adapt / reject`)와 수정·제작을 진행합니다. 공개 검증기는 Gemini 원출력 버전과 사람 승인 버전, 파일 해시 연결을 요구하므로 실제 원출력과 사람 채택 이력을 그대로 보존합니다.

## 다른 에이전트에게 첨부하는 법

새 작업은 [단계별 진행](docs/WORKFLOW.md)에 따라 워크플로와 이번 경로에서 쓰는 매뉴얼을 처음부터 끝까지 읽고 작품별 체크리스트를 만듭니다. 단계마다 해당 문서를 다시 읽고 실제 원고·입력·결과에 적용했는지 확인한 뒤 다음 단계로 넘어갑니다. 자료 첨부나 기술 검사 PASS만으로는 실제 작법·배치 퇴고를 대신할 수 없습니다. AGY에는 내부 체크리스트를 작업지시서로 넘기지 않고 짧은 자연어와 실제 작품·매뉴얼·예시로 부탁합니다.

Claude Code 클라우드에서 기존 스킬 저장소와 Google Drive를 함께 쓰려면 [클라우드 집필 연결](docs/CLOUD_WRITING.md)(2026-10-09 확인 기록)을 참고하세요. 이 공개 키트는 이식 가능한 배포본이며 개인 비공개 제작 환경 전체를 포함하지 않습니다.

저장소 전체를 작업공간에 넣고 다음 문장을 전달하세요.

```text
이 저장소의 AGENTS.md와 skills/community-webtoon-producer/SKILL.md를 먼저 끝까지 읽어라.
docs/WORKFLOW.md와 이번 경로의 매뉴얼도 끝까지 읽고 작품별 체크리스트를 만들어줘.
단계에 들어갈 때 해당 매뉴얼을 읽고, 끝날 때 실제 적용을 체크한 뒤 다음 단계 문서를 읽어줘.
역할과 창작 인계 문서도 읽고, 내가 무엇을 왜 만들려는지 함께 정리해줘.
이미 정한 의도와 현재 작업이 있으면 이어받아, 지금 필요한 단계부터 진행해줘.
생성할 때는 채택한 콘티와 실제 입력의 원문·화자·참조를 검증해줘.
```

에이전트가 저장소 전체의 루트 `AGENTS.md`와 스킬 파일을 직접 읽게 하면 됩니다. `skills/community-webtoon-producer` 폴더만 개인 스킬 경로에 복사해도 루트의 `docs/`와 `harness/`는 함께 설치되지 않으므로, 참조할 전체 저장소도 작업공간에 유지해야 합니다.

## 빠른 시작

프로젝트 초기화와 검증 스크립트에는 Python 3.10 이상 표준 라이브러리만 필요하며 외부 패키지는 없습니다. 실제 이미지 생성에는 Node.js 20+와 별도 설치한 `ima2-gen`이 필요합니다.

```bash
python harness/scripts/init_project.py --root work --slug my-first-toon --title "첫 커뮤니티툰"
```

생성된 프로젝트의 `PROJECT.md`부터 열고 다음 순서로 진행합니다. (아래 7-10단계의 `validate_project.py` 잠금은 기존 `page_id` 기반 양식을 기준으로 동작하며, 1-2컷 시트 제작과 세로 편집·업로드 분할을 함께 쓸 때는 [컷 기반 제작](docs/CUT_BASED_PRODUCTION.md)과 [업로드와 무손실 분할](docs/UPLOAD_DELIVERY.md)을 함께 참고하세요.)

1. `01_sources/source_ledger.md`: 사실, 분위기, MSG, 사용 금지를 분리합니다.
2. `02_direction/creative_brief.md`: 사용자 의도, 커뮤니티 기대, 만화 가독성의 교집합을 승인받습니다.
3. `03_conte`에 Director/Producer의 거친 장면 뼈대나 원안을 먼저 보존합니다. 빈칸 채우기를 맡길 때는 빈칸을 미리 메우지 않고, 자유 집필이나 완성문 퇴고를 맡길 때는 해당 위임 범위를 분명히 적습니다.
4. 원안과 사실/MSG 경계를 Gemini에게 전달해 집필·연출 패스를 받고, 원출력을 별도 파일로 보존해 사용자에게 먼저 그대로 보여줍니다.
5. 제안별로 `adopt / adapt / reject`를 정리한 뒤, 전편(감정·인과·보상) → 장면 연결 → 컷 설계 순서로 퇴고해 하나의 canonical 콘티를 만들고 사람이 직접 수정하거나 승인합니다. 무엇을 왜 유지·수정했는지는 기존 콘티 메모에 남기며 매 컷 별도 보고서를 추가하지 않습니다.
6. `04_locks/editorial_review_lock.csv`에 원 뼈대, Gemini 원출력, 공동 검토, 사람 승인본의 버전·근거 파일과 해시를 기록합니다.
7. `04_locks`: 화면 텍스트, 화자, 캐스트, 레퍼런스를 잠급니다.
8. `generation_plan.csv`에서 각 페이지를 `independent_page`, `same_scene_continuation`, `reused_shot_variation` 중 하나로 잠급니다.
9. `generation_plan.csv`의 `runtime`을 기본값 `ima2-gen`으로 기록하고, `05_prompts`에 각 생성 단위가 독립적으로 완전한 provider-bound 프롬프트를 갖게 합니다.
10. 생성 전 검사를 실행합니다.

```bash
python harness/scripts/validate_project.py --project work/my-first-toon --stage pre-generation --strict
```

11. 사용자 생성 승인 뒤 승인된 장수·비용 범위 안에서 `ima2-gen`으로 최소 3개 이상의 독립 후보를 빠르게 확보하고 사람이 직접 고릅니다. 연기·표정·액션·반전·분위기가 중요한 구간은 4-6개를 우선합니다. 첫 도입이나 입력 변경 시 수행하는 파일럿은 실제 전달 확인이 목적이며 매번 작은 배치만 강제하는 뜻이 아닙니다.
12. 승인된 수량·재시도 범위 안에서 한 후보가 실패하면 성공한 작업을 건드리지 않은 채 실패분만 다음 실행 파동 맨 앞에 재투입하고, 마지막 파동 뒤에도 남은 실패를 숨기지 않고 보고합니다. 사용자의 수량·재시도 제한을 항상 우선합니다.
13. 사람이 고른 원본의 구조와 핵심 연기는 맞지만 식자나 몇 곳의 국소 오류만 남았으면 `harness/templates/post_selection_page_finish_request.md`로 선택 원본을 보존한 채 전체 식자와 지정된 시각 수정을 한 번에 시험할 수 있습니다. 사용자가 기존 글자를 그대로 유지하기로 결정한 경우에는 그 결정을 보존합니다. 구조·인과·정체성이 틀리면 재생성합니다.
14. 검토할 후보는 순서대로 정렬한 원본 이미지 폴더로 전달합니다. P001의 모든 후보 다음 P002의 모든 후보가 오게 이름을 정하고, 기존 전달 폴더를 보존합니다. 후보 비교·열람 HTML은 사용자 명시 요청 때만 만듭니다. 1-2컷 시트 제작에서는 선택된 컷들의 실제 위아래 흰 여백을 재어 목표 거리에서 부족한 간격만 더해 세로 원고로 조립하고, 전체 보기본과 안전한 흰 여백 기준의 무손실 분할본(디시 기준 파일당 20,000,000바이트 미만·세로 9,000px 이하)을 준비합니다.
15. 최종 승인 후 완성본, 승인 원본, 실제 사용 소재를 복사하고 SHA-256 해시와 함께 동결합니다.

```bash
python harness/scripts/freeze_completion.py \
  --project work/my-first-toon \
  --archive-root completed \
  --final-list work/my-first-toon/07_logs/final_files.txt \
  --approved-list work/my-first-toon/07_logs/approved_sources.txt \
  --materials-list work/my-first-toon/07_logs/used_materials.txt \
  --apply
```

승인된 생성지침의 WHY·문맥·예시를 실제 입력에 그대로 전달하는 방법은 [provider 입력 보존](docs/PROVIDER_ADAPTER.md#생성지침의-why와-문맥-전달)을 따릅니다. 부정형 주의사항을 분리하더라도 그 주변 이유까지 축약하지 않습니다.

## 결과를 바꾸는 제작 규칙

- 커뮤니티 반응을 추측하지 않고 실제 소스와 MSG를 분리합니다.
- 펀치라인부터 바로 그리지 않고, 전편의 감정·인과·보상 → 장면 연결 → 컷 설계 순서로 퇴고합니다.
- 장면 이해에 꼭 필요한 발화자·상대·반응·핵심 볼거리는 살리고, 불필요한 구경꾼·반복 배경·연속성 부담만 덜어냅니다. 인물 수 자체를 기계적으로 줄이지 않습니다.
- 화면에 실제로 보일 면과 글자만 작화 묘사에 적고, 소품의 이야기상 이유는 전체 맥락으로 전달합니다.
- 생성 전에 대사 내용뿐 아니라 대사가 **누구에게 어디로 붙는지**와 폰 표시 폭에서 읽힐 글자·대비·말풍선 공간의 목적을 함께 전달합니다.
- 생성 시트 안의 컷 배치와 최종 세로 스크롤 편집을 분리하고, 컷 사이 거리는 `앞 컷 아래 흰 여백 + 추가 간격 + 다음 컷 위 흰 여백`으로 계산합니다.
- 생성 성공과 창작 승인을 분리합니다. 데스크톱 축소 확인과 실제 기기 확인을 구별하며, 최종 미감 판단은 사람이 합니다.

처음 사용하는 사람과 에이전트는 반드시 [사용 전 준비와 품질 전제](docs/BEFORE_YOU_START.md)를 먼저 확인하세요. 특히 반복 등장 캐릭터를 고정하려면 사용자가 미리 레퍼런스 파일을 준비하고 역할별로 매핑해야 합니다. 프롬프트만으로 동일 캐릭터를 유지하는 것은 이 키트의 품질 보장 범위가 아닙니다.

자세한 기준은 [품질 계약](docs/QUALITY_CONTRACT.md), [작법 퇴고](docs/CRAFT_REVIEW.md), [컷 기반 제작](docs/CUT_BASED_PRODUCTION.md), [업로드와 무손실 분할](docs/UPLOAD_DELIVERY.md), [provider 연결 안내](docs/PROVIDER_ADAPTER.md)를 참고하세요.
