# Provider Adapter Contract

이 키트의 현재 검증된 기본 실제 이미지 실행기는 별도 설치하는 [**ima2-gen**](https://github.com/lidge-jun/ima2-gen)입니다. 실제 생성은 `ima2-gen`의 CLI/server 경로로 수행하며, 별도 shim이나 성공을 흉내 내는 우회 경로를 만들지 않습니다. 다른 provider/runtime으로 교체할 수는 있지만 아래 입력·증거 계약은 그대로 지켜야 합니다.

공개 저장소(`Q0916/community-webtoon-agent-kit`)는 Python 3.10+ 표준 라이브러리 기반의 초기화·검증·동결 스크립트(`init_project.py`, `validate_project.py`, `provider_instruction_integrity.py`, `freeze_completion.py`, `verify_repository.py`)만 제공합니다. 생성 runner, 누적 receipt 분석기, 1-2컷 시트 분리·재배치 도구, 업로드 무손실 분할 도구는 공개 키트 자체에 포함되지 않습니다.

기본 실행 예시는 `ima2 gen "..."`이며 설치형 CLI가 없으면 `npx ima2-gen <command>`를 사용합니다. 서버 주소가 필요할 때는 실행 출력이나 `ima2`의 server state를 확인하고 특정 포트를 임의로 가정하지 않습니다.

긴 만화 입력은 실제 사용할 CLI에서 `gen --stdin --mode direct` 지원 여부를 확인한 뒤, UTF-8 파일 바이트를 subprocess의 stdin으로 직접 전달합니다. PowerShell 문자 파이프나 명령줄 인수로 긴 전문을 옮기지 않습니다. 문서 첨부 방식은 파일 해시가 같더라도 도구 내부에서 본문이 다시 요약될 수 있으므로 전문 전달 성공으로 취급하지 않습니다. 실제 참조 이미지는 별도로 첨부하고 각 이미지의 역할을 본문에 적습니다. 문서 첨부 경로는 사용자가 명시적으로 선택한 경우에만 씁니다.

프롬프트 앞부분에는 작품 전체 흐름과 의도, 현재 구간의 인과적 역할과 앞뒤 상태, 정확한 대사와 가독성 목적, 표현 예산의 WHY와 협력 요청, 채택 배치와 대응 원문을 먼저 둡니다. 그 뒤에 승인된 provider 전문과 필요한 콘티·원문을 실제로 넣습니다. 긴 입력을 줄여야 할 때는 확인된 중복과 뒤쪽 부록부터 검토하며, 앞에 놓인 이유(WHY)와 승인 문구를 자동 요약하지 않습니다.

기존 전체 페이지 프로필에 적힌 60%/78% 표현 예산은 작업 가설이지 provider 내부 토큰이나 기제를 계측한 사실이 아닙니다. 또한 전체 페이지 프로필의 예산 비율이나 특정 작품의 크기·여백 수치를 새 컷 시트 프로필(`docs/CUT_BASED_PRODUCTION.md`)과 억지로 합치지 않고 구별해 다룹니다.

실행기가 반환하는 `revisedPrompt` 등 실제 전송 증거와 원본을 대조합니다. 파일 해시 일치, 본문 전달 성공, 창작 품질 합격은 서로 다른 확인 단계입니다. 요청한 모델이 보이지 않을 때는 기존에 성공했던 서버의 실행기와 카탈로그를 먼저 확인하며, 모델을 조용히 바꾸거나 설치·공유 서버 구성을 임의로 변경하지 않습니다.

## 입력

- provider-bound prompt 한 개 (기존 전체 페이지 프로필의 페이지 프롬프트 또는 `docs/CUT_BASED_PRODUCTION.md`의 분리 가능한 1-2컷 시트 프롬프트)
- generation plan에 기록된 실제 `runtime` 이름(기본값 `ima2-gen`)
- 작품 전체 이야기, 독자 감정 순서, 현재 구간/장면의 이유와 앞뒤 상태, 정확한 대사, `fact`/`MSG` 경계
- generation plan에 잠근 `scene_relation`
- 해당 장면의 character/style/continuity reference 목록
- 출력 디렉터리
- 페이지/시트 ID와 시도 ID
- 기술 사전검사 결과
- 사용자의 현재 생성 수량·범위 승인 근거

각 프롬프트는 다른 전역 문서를 읽지 않아도 그 자체로 완결되어야 합니다. 기존 전체 페이지 프로필을 검증할 때는 `COMMUNITY_TOON_GENERATION_CONTRACT_V1` 블록과 작품 공통 이해, 페이지별 캐스트·텍스트·소품·구도 정보가 같은 `05_prompts/*.txt` 파일 안에 있어야 합니다. 공개 `validate_project.py`는 이 page ID 기반 기존 잠금을 검사하며, 새 컷 시트 프로필의 분리·편집 구성을 자동 검증한다고 주장하지 않습니다.

어느 프로필이든 화면에 실제로 보일 면과 문자만 작화 묘사에 넣되, 소품이 등장하는 이야기상 이유와 모바일 축소 환경에서 글자·대비·말풍선 공간이 필요한 목적은 본문 맥락으로 분명히 전달합니다.

Adapter는 ID나 제출 순서에서 continuity를 임의로 추론하지 않습니다. `independent_page`에는 scene-continuity reference가 없어야 하고, `same_scene_continuation` 또는 `reused_shot_variation`에는 선언된 scene reference가 붙어야 합니다.

## 생성지침의 WHY와 문맥 전달

승인된 provider 스킬은 임의 요약용 참고 자료가 아니라 실제 입력 본문이다. 원문의 목적·인과·예시·협력 요청을 그대로 보존하고 그 위에 작품별 장면을 이어 붙인다. ‘가설’이나 ‘협력’이라는 단어와 숫자 비율만 남긴 축약본은 문맥을 전달한 증거가 될 수 없다. 넓은 흰 여백과 간결한 주변 묘사는 중요한 얼굴·손·몸짓·소품·글자를 더 선명하게 살리려는 수단이므로, 핵심 볼거리와 연기를 충분히 보여주는 목표와 함께 다룬다.

사용자가 부정형·보험 문구 분리를 요청하면 해당 문구만 내부 주의사항으로 옮기고, 주변 WHY와 예시는 그대로 유지한다. 필요한 긍정형 변경은 원문 해시와 정확한 before/after, 변경 이유, 사용자 결정 근거를 갖춘 내부 목록으로 관리한다. 내부 주의사항과 변경 목록은 생성 모델에 첨부하거나 발췌·링크로 넣지 않는다. 이미 승인받은 범위는 반복해서 다시 묻지 않는다.

본문 조립과 기존 사전검사 연결:

```bash
python harness/scripts/provider_instruction_integrity.py --source approved-provider.md --emit provider-body.txt
python harness/scripts/validate_project.py --project work/my-first-toon --stage pre-generation --strict --provider-instruction approved-provider.md
```

첫 명령으로 만든 파일의 전문을 각 `05_prompts/*.txt`에 삽입한다. 승인된 변경이 있으면 조립에는 `--amendments`, 검증에는 `--provider-amendments`로 같은 JSON을 전달한다. JSON 형식은 `{"source_sha256":"원문 파일 SHA-256","changes":[{"before":"유일한 원문 구절","after":"승인된 변경 구절","reason":"변경 이유","user_decision_reference":"실제 사용자 결정 근거"}]}`다. BOM·줄바꿈·YAML 설치 메타데이터 차이만 전송 형식 차이로 처리한다. 자동 검사는 텍스트 보존과 근거 필드의 존재를 확인하며, 사용자 승인 사실과 의미는 제작자가 확인한다.

준비 단계에서 원문 대조를 한 번 수행하고, 별도 실행기가 그 결과에 프롬프트·원문·변경 목록의 해시를 묶어 두었다면 제출 직전에는 해시 검사만으로 변경 여부를 확인할 수 있다. 다만 이 공개 키트의 검증 보고서만으로 제출 시점의 해시 결합까지 자동 제공된다고 해석하지 않는다. 그러한 실행기가 없으면 실제 제출 입력을 다시 대조한다. `--provider-instruction`을 생략한 기존 호환 경로는 provider 전문 보존을 검사했다고 주장할 수 없다.

규칙을 줄이기 전에는 그 규칙이 막아 주던 실패와 이유(WHY)를 먼저 확인한다. 첫 입력부터 축약됐는지 확인하는 전문 대조와, 검증 뒤 파일이 바뀌었는지 확인하는 해시 검사는 역할이 다르다. 이유가 불명확한 항목은 함부로 지우지 않고 유지하며, 같은 역할을 중복 수행하는 부분만 통합한다.

## 출력 증거

provider adapter는 가능한 범위에서 다음을 남깁니다.

- 실제 전송한 prompt 또는 그 SHA-256
- 실제 첨부한 reference 경로와 SHA-256
- provider/model/size/quality 파라미터
- 요청 식별자(request/job ID)와 제출 시각·완료 시각
- 생성 파일 경로와 바이트 크기
- 오류 원문

`refsCount: 3`처럼 개수만 남기는 기록은 실제로 어떤 파일이 붙었는지 증명하지 못합니다.

## 파일럿

첫 파일럿은 다음을 확인합니다.

1. 한국어가 provider까지 손상 없이 전달됐는가?
2. 올바른 레퍼런스 파일이 붙었는가?
3. 흰 원고지 또는 분리 가능한 1-2컷 시트 구조가 prompt에 실제 포함됐는가?
4. 출력이 정상 완료됐는가?

1-3은 첫 실행기 도입이나 입력 변경 시 실제 전달을 확인하는 기술 검증이고, 생성된 이미지의 매력과 채택 여부는 사람 검수입니다. 파일럿은 전달 확인 절차이지 이후 모든 본생성을 작은 배치로만 제한하라는 뜻이 아닙니다.

## 대량 병렬 후보 탐색

이미지 생성은 **사용자가 승인한 장수·비용 범위 안에서 단위 시간당 사람이 고를 만한 후보 수를 우선하는 병렬 샘플링**으로 운영합니다. 예를 들어 한 시간 동안 오류 없이 10장을 만드는 것보다, 10분에 100번 시도해 마음에 드는 10장을 얻는 편이 실제 제작에 더 유리할 수 있습니다. 다만 이 예시는 설명을 위한 비유일 뿐 모든 작업의 장수나 비용 승인을 대신하지 않으며, 언제나 사용자가 정한 수량·재시도 상한이 우선합니다.

- **후보 풀·wave·동시 실행 수의 구별**: 확보할 전체 후보 풀(예: 최소 3안 또는 4–6안 이상), 한 번에 묶는 wave 크기, 실제 서버·제공자의 동시 실행 병렬 수를 서로 구별해 설정합니다.
- **개별 실패율과 실행 모드**: 개별 실패나 타임아웃을 감수하고 먼저 성공한 결과부터 사람이 고를 수 있게 전달합니다. 개별 실패율이 올랐다는 이유만으로 3–8개 같은 소규모 보수 모드로 자동 전환하지 않습니다. 보수적 축소는 사용자의 명시적 요청이 있거나 과부하로 인해 단위 시간당 실제 완료량이 떨어질 때만 선택합니다.
- **실제 처리량 기준 판단**: 로컬 접수 상한만 올렸다고 해서 제공자의 실제 실행 슬롯까지 늘어난 것처럼 보고하지 않습니다. 단위 시간당 실제 완료 후보 수로 병목을 판단하며, 실행 중인 다른 작업과 공유 서버를 보호합니다.
- **원본·식별자 보존과 늦은 성공 회수**: 원문·참조·성공 원본과 request/job 식별자를 보존합니다. 타임아웃 뒤 늦게 완료된 결과도 요청 식별자로 회수하고, 실제로 확인된 누락분만 보충합니다. 모든 요청이 끝날 때까지 기다리느라 이미 확보한 후보 전달을 늦추지 않으며, 최종 시각 선택은 사용자가 맡습니다.

[Best-of-N sampling](https://huggingface.co/docs/trl/v0.19.0/best_of_n)은 여러 후보를 생성한 뒤 좋은 결과를 고르는 구조를 가리킵니다. 이 워크플로에서는 최종 선별을 사람이 맡습니다. 병렬 수와 실제 완료 처리량을 맞추는 운영은 [throughput optimization](https://docs.nvidia.com/deeplearning/triton-inference-server/user-guide/docs/user_guide/optimization.html)에 가깝습니다.

## Sidecar 운영

긴 생성은 대화 밖 sidecar로 실행할 수 있습니다(공개 키트에 별도 runner가 내장된 것은 아니며 실행 환경에서 구성). 요청이 접수됐거나 active 상태가 된 것을 한 번 확인한 뒤에는, 완료 알림이나 사용자의 상태 확인 요청이 오기 전까지 반복 폴링하지 않습니다.

사용자가 승인한 수량·재시도 범위 안에서 독립 job 하나가 실패했고 뒤의 job이나 다음 wave가 남아 있다면, 전체 완료까지 기다렸다가 뒤늦게 발견하지 않습니다. 실패한 job만 다음 live wave의 맨 앞에 즉시 승계하고, 이미 성공했거나 실행 중인 job과 서버는 취소·재부팅하지 않습니다. 마지막 ordinary wave 뒤에도 남은 실패는 승인된 범위 안에서 한 번 별도 tail retry하고, 그래도 실패하면 재시도 입력과 오류 원문을 보존한 채 partial 상태로 보고합니다.
