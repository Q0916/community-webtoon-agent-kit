# 사용 전 준비와 품질 전제

이 문서는 사용자가 이미 습관처럼 하고 있어서 지침에서 빠지기 쉬운 준비 작업을 명시합니다. 아래 `필수` 항목을 생략하면 같은 캐릭터, 같은 말맛, 같은 페이지 문법, 같은 완성도를 기대할 수 없습니다.

## 1. 먼저 알아야 할 품질 범위

이 키트는 제작 과정의 재현성을 높입니다. 특정 이미지 모델의 성능, 랜덤 시드, 계정별 모델 버전, 생성 서비스의 정책 변화까지 고정하지는 못합니다.

다음 조건이 충족될수록 결과가 안정됩니다.

| 준비 | 중요도 | 빠졌을 때 생기는 문제 |
|---|---|---|
| 실제 소스와 반응 표본 | 필수 | 커뮤니티 말투와 여론을 에이전트가 지어냄 |
| 작품 전체 문맥과 참여자 이해 일치 | 필수 | 미시 지시는 지켰지만 이야기·감정·장면 이유가 다른 결과가 나옴 |
| 사용자의 해석과 스윗스팟 승인 | 필수 | 정보는 맞지만 사용자가 원한 만화가 아님 |
| 반복 캐릭터 identity reference | 필수 | 매 컷 얼굴·의상·실루엣이 달라짐 |
| 캐릭터 역할 매핑과 해시 | 필수 | 다른 캐릭터 레퍼런스가 섞이거나 잘못 첨부됨 |
| 인과 콘티 승인 | 필수 | 정보 카드 나열 또는 갑작스러운 펀치라인이 됨 |
| Gemini 콘티 검수·버전업 | 필수 | GPT 초안의 말맛·장면 선택 오류를 자체 검사로 놓침 |
| 사람의 콘티 직접 수정·최종 승인 | 필수 | 모델끼리 합의한 결과를 사용자 취향으로 오인함 |
| 텍스트 source/routing lock | 필수 | 대사가 바뀌거나 엉뚱한 화자·소품에 붙음 |
| 작은 파일럿과 사람 검수 | 필수 | 기술적으로 성공한 실패물을 전체 배치로 확대함 |
| continuity reference | 연속 장면에 필수 | 배경·군중·카메라가 컷마다 새로 리셋됨 |
| turnaround/expression 보조 시트 | 권장 | 포즈 변화에서 정체성이 약해짐 |
| 후속 식자 도구 | 긴 정확 한국어에 권장 | 이미지 모델의 한글 오탈자 위험이 커짐 |

## 2. 고정 캐릭터는 먼저 레퍼런스를 준비한다

반복 등장 캐릭터는 이름과 설명만으로 고정하지 않습니다. 최소한 아래 파일을 사용자가 직접 보고 선택해야 합니다.

### 최소 팩

1. `identity_primary` — 정면 또는 3/4 시점에서 얼굴, 머리, 체형, 핵심 의상이 명확한 무텍스트 기준 이미지.
2. 가능하면 `turnaround` — 앞·옆·뒤 또는 전신 비율을 보여주는 시트.
3. 가능하면 `expression_detail` — 표정과 제스처 범위를 보여주는 보조 시트.

무텍스트를 권장하는 이유는 레퍼런스 안의 글자, 말풍선, UI, 다른 캐릭터가 이후 생성에 오염원으로 들어가기 쉽기 때문입니다.

### 좋은 identity reference 조건

- 캐릭터 한 명이 명확하게 보입니다.
- 얼굴, 헤어, 체형, 의상 색, 실루엣을 판별할 수 있습니다.
- 다른 캐릭터, 대사, 로고, 복잡한 배경이 최소화되어 있습니다.
- 패널 연출보다 “이 캐릭터가 누구인가”를 설명하는 이미지입니다.
- 사용자가 직접 보고 이 파일을 정본으로 승인했습니다.

### 매핑 절차

1. 캐릭터에 안정적인 `role_id`를 부여합니다. 예: `CHAR_GEM_01`.
2. 파일에 `reference_id`를 부여합니다. 예: `REF_GEM_IDENTITY_V1`.
3. `04_locks/reference_manifest.csv`에 역할, 경로, ref 역할을 기록합니다.
4. SHA-256을 계산해 기록합니다.
5. 사용자가 파일을 직접 보고 맞는 역할인지 확인한 뒤 `visual_role_verified=true`로 바꿉니다.
6. 등장 페이지의 `page_cast_lock.csv`에서 `role_id`와 `reference_id`를 연결합니다.
7. 서로 다른 캐릭터가 같은 SHA-256을 가리키면 생성하지 말고 매핑부터 고칩니다.

예시:

```csv
reference_id,role_id,ref_role,ref_path,sha256,visual_role_verified,notes
REF_GEM_IDENTITY_V1,CHAR_GEM_01,identity_primary,assets/characters/gem_identity_v1.png,ABC123...,true,user approved
```

이 저장소는 이미지 파일을 포함하지 않으므로 `assets/characters/`는 각 사용자가 직접 준비합니다. 이미지 파일은 공개 Git에 올리지 않아도 되며, 로컬 경로와 해시만 프로젝트 매니페스트에 남길 수 있습니다.

## 3. 캐릭터 시트와 연속 장면 레퍼런스는 역할이 다르다

- identity reference: 캐릭터가 누구인지 고정합니다.
- turnaround/expression reference: 형태와 연기 범위를 보조합니다.
- style reference: 선, 채색, 질감만 안내합니다.
- scene-continuity reference: 직전 장면의 무대, 군중, 카메라, 배치를 이어갑니다.

직전 패널만 붙이고 identity reference를 빼면 캐릭터가 서서히 변할 수 있습니다. 반대로 캐릭터 시트만 붙이고 continuity reference를 빼면 같은 장소가 매번 다시 설계됩니다. 연속 장면에서는 두 종류를 함께 씁니다.

단, `다음 페이지`라는 이유만으로 continuity reference를 붙이지 않습니다. 생성 계획에서 먼저 관계를 잠급니다.

- `independent_page`: 대화·정보·리액션의 다음 비트이지만 샷과 물리적 장면 상태는 새로 구성해도 됨.
- `same_scene_continuation`: 같은 장소·시간·배치·행동이 실제로 이어짐.
- `reused_shot_variation`: 같은 샷을 유지한 채 표정·소품·부분 동작만 변형함.

독립 페이지에는 identity reference만 사용합니다. 나머지 두 관계에는 identity reference를 유지하면서 scene reference를 별도로 붙입니다.

## 4. 커뮤니티 소스도 사용자가 기준을 준다

에이전트가 인터넷을 볼 수 있어도 무엇을 재미있다고 읽을지는 자동으로 결정되지 않습니다. 최소한 다음을 준비하거나 승인해야 합니다.

- 핵심 anchor 글 또는 사건.
- 사실로 유지해야 할 내용.
- 커뮤니티에서 실제로 관측된 말투·댓글·밈.
- 사용자가 넣고 싶은 해석이나 공격 방향.
- 과장 가능한 MSG와 건드리면 안 되는 선.

실시간 주제는 표본을 좁게 잡습니다. 오래된 인기글을 많이 섞으면 현재 사건의 분위기가 아니라 일반적인 커뮤니티 이미지로 평준화됩니다.

## 5. 콘티는 정보 요약과 다르다

에이전트가 자료를 잘 요약했다고 이미지 생성으로 넘어가면 안 됩니다. 모든 컷에 다음 네 값이 채워져야 합니다.

1. 이전 컷에서 왜 넘어오는가.
2. 독자가 먼저 무엇을 보는가.
3. 인물이 방금 무엇을 알거나 오해하는가.
4. 그래서 다음 컷이 왜 발생하는가.

이 네 칸 중 하나가 비면 아직 콘티가 아니라 자료 배치입니다.

### GPT/Codex 단독 콘티 품질은 보증하지 않는다

콘티는 프론트 창작 작업입니다. GPT/Codex가 소스와 필수 필드를 잘 채워도 말맛, 장면 선택, 개그 타이밍, 독자 보상까지 안정적으로 맞는다고 보증할 수 없습니다. 따라서 다음 단계가 필수입니다.

1. GPT/Codex 초안 또는 최초 콘티를 `v1`로 보존합니다.
2. Gemini가 같은 소스 근거와 `v1`을 읽고 검수 의견과 수정 콘티 `v2`를 만듭니다.
3. 사람은 `v1`, Gemini 검수, `v2`를 직접 비교하고 필요하면 `v3`로 수정합니다.
4. 사람이 최종 승인한 버전만 `current_version`으로 기록합니다.
5. `editorial_review_lock.csv`에 Gemini와 human 두 행을 모두 남기고 각 검수 근거 파일의 SHA-256을 기록합니다.

Gemini를 사용할 수 없는 다른 에이전트는 이 단계를 자동으로 다른 GPT 자기검수로 대체하면 안 됩니다. 사용자에게 검증된 워크플로를 완수할 수 없다고 알리고, Gemini 검수를 받을 때까지 생성 단계로 넘어가지 않습니다.

## 6. 화면 글자는 내용과 소유자를 따로 잠근다

대사 목록만 주면 이미지 모델은 누가 말하는지 추측합니다. 모든 렌더 텍스트에 다음을 기록합니다.

- `text_id`
- 실제 렌더할 문구
- `user-approved MSG`, `gallery phrase`, `source-function adaptation`, `SFX/prop/title` 중 source class
- `text_owner`
- `owner_role`: speech, thought, caption, sign, SFX, prop, comment 등
- `attachment_hint`: 말풍선 꼬리 대상, 댓글 카드, 표지판 내부 등
- `read_order`

`needs user approval` 상태의 문구가 하나라도 있으면 글자가 포함된 본생성을 시작하지 않습니다.

## 7. 이미지 생성 전에 사용자가 승인해야 하는 것

현재 키트의 기본 이미지 생성 실행기는 `ima2-gen`입니다. 실제 생성 전에 Node.js 20+와 ima2-gen의 실제 CLI/server가 동작하는지 확인하고, `generation_plan.csv`의 `runtime`에 `ima2-gen`을 기록합니다. 다른 실행기를 쓰면 그 실제 이름을 기록하되 같은 입력·증거 계약을 지킵니다.

최소 승인 목록:

- 주제와 해석
- 스윗스팟
- 캐릭터 스탠스와 등장 범위
- 인과 콘티
- Gemini가 검수·버전업한 콘티와 근거 파일
- 사람이 직접 수정하거나 최종 승인한 콘티 버전
- 렌더할 문구
- 고정 캐릭터 정본 레퍼런스
- 파일럿으로 생성할 페이지 범위

에이전트가 만든 기술 PASS 보고서는 이 승인을 대신하지 않습니다.

## 8. 파일럿에서 확인할 것

에이전트의 객관 확인:

- 올바른 prompt와 reference가 실제 provider에 전달됐는가.
- 한국어가 로그에서 `?`로 깨지지 않았는가.
- 파일이 생성됐고 크기와 경로가 기록됐는가.
- 페이지 prompt 안에 흰 원고지와 텍스트·캐스트 계약이 들어 있는가.

사용자의 시각 확인:

- 캐릭터가 정본처럼 느껴지는가.
- 표정과 장면의 말맛이 맞는가.
- 흰 여백과 그림 블록의 리듬이 맞는가.
- 말풍선과 UI가 읽히는가.
- 이 방향으로 나머지 페이지를 생성해도 되는가.

## 9. 다른 에이전트용 실행 지시문

저장소를 첨부한 뒤 다음을 그대로 전달할 수 있습니다.

```text
AGENTS.md, docs/BEFORE_YOU_START.md, docs/QUALITY_CONTRACT.md,
skills/community-webtoon-producer/SKILL.md를 먼저 끝까지 읽어라.

내가 주는 소스와 캐릭터 레퍼런스를 먼저 점검하고, 반복 캐릭터의 role_id,
reference_id, ref_role, SHA-256, visual_role_verified 상태를 매핑하라.
레퍼런스가 없거나 사용자 승인이 없으면 캐릭터 일관성을 보장한다고 말하지 말고 멈춰라.

source ledger -> sweet spot 승인 -> 인과 콘티 -> Gemini 콘티 검수·버전업 ->
사람의 콘티 수정/최종 승인 -> text/cast/reference locks -> provider prompt ->
strict pre-generation validation 순서로 진행하라.
GPT/Codex의 자체 콘티 검사는 프론트 창작 품질 보증이 아니며 Gemini와 사람 검수를 대체할 수 없다.
내가 명시적으로 생성 범위를 승인하기 전에는 이미지를 생성하지 마라.
생성 후에는 후보를 임의 선별하지 말고 내가 직접 볼 수 있게 전달하라.
```

## 10. 같은 결과를 보장할 수 없는 경우

- 고정 캐릭터 레퍼런스 없이 이름과 말로만 반복 생성을 요구하는 경우.
- 실제 커뮤니티 소스 없이 “그럴듯한 분위기”를 만들어 달라는 경우.
- 사용자 방향 승인 없이 에이전트가 알아서 스윗스팟을 결정한 경우.
- 인과 콘티 없이 바로 페이지 프롬프트를 만든 경우.
- 긴 정확 한국어를 이미지 모델 한 번에 맡기면서 후속 식자를 허용하지 않는 경우.
- 파일럿 검수 없이 전체 배치를 생성한 경우.
- 이전 반려본과 현재 정본을 같은 후보·레퍼런스 폴더에 섞은 경우.

이 경우 에이전트는 결과를 과장해 보장하지 말고, 빠진 준비 단계를 먼저 복구해야 합니다.
