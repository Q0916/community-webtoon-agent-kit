# 사용 전 준비와 품질 전제

특갤툰을 보고 제작 과정이 궁금해져 공개 저장소(`Q0916/community-webtoon-agent-kit`)를 찾은 독자와 에이전트를 위한 사전 점검 문서입니다. 작업자가 평소 당연하게 챙기다 보니 지침에서 빠지기 쉬운 준비 항목을 정리했습니다. 아래 `필수` 항목을 건너뛰면 같은 캐릭터, 같은 말맛, 같은 화면 호흡과 완성도를 재현하기 어렵습니다.

## 1. 먼저 알아야 할 공개 키트의 범위와 제작 방식

이 키트는 만화 제작의 의사결정 구조와 입력·검증 절차를 재현합니다. 특정 이미지 모델의 성능, 랜덤 시드, 계정별 모델 버전, 생성 서비스의 정책 변화까지 고정하지는 못합니다.

### 공개 저장소가 제공하는 도구와 별도 준비 환경

- **공개 키트 포함 도구(Python 3.10+ 표준 라이브러리만 사용)**: `init_project.py`, `validate_project.py`, `provider_instruction_integrity.py`, `freeze_completion.py`, `verify_repository.py`
- **사용자 별도 설치·준비 대상**: 기본 실제 이미지 실행기인 `ima2-gen`(별도 설치)을 비롯해 백그라운드 생성 runner, 누적 receipt 분석기, 1~2컷 시트 분리·재배치 도구, 세로 원고 편집 환경, 커뮤니티 업로드용 무손실 분할·높이/용량 검사 도구는 공개 키트에 포함되지 않습니다.

### 두 가지 제작 프로필의 구별

이 저장소는 이전 세대 작품을 재현하는 **전체 페이지 프로필**과 최신 **컷 시트 생성 후 세로 편집 방식**을 구별해 다룹니다.

1. **기존 전체 페이지 프로필**: 9월 12일 수학자툰, Amazon × OpenAI 사례 등 초기 작품의 재현 기준입니다. 공개 `validate_project.py`는 이 방식의 page ID 기준 잠금(`04_locks/`, `05_prompts/` 등)을 직접 검사합니다.
2. **최신 컷 기반 제작 및 세로 스크롤 편집 방식**(`docs/CUT_BASED_PRODUCTION.md`, `docs/CRAFT_REVIEW.md`, `docs/UPLOAD_DELIVERY.md`): 2026-10-17 완성한 꾸준툰 새로쓰기(최종 승인 65컷, 2026-10-21 높이·용량 조정본 13구간)와 2026-10-21 완성한 미소녀툰 「왜 특갤러들은 미소녀가 되고 싶어 하는가」(선택 21컷, 최종 4구간)의 컷 생성·선택·편집 경험을 바탕으로 정리한 신작 기준입니다. **작품과 의도 이해 → 전편의 감정·인과·보상 퇴고 → 장면 연결 → 컷 설계 → 전체 흐름/현재 구간/앞뒤 상태/정확한 대사/WHY를 담은 실제 입력 → 분리 가능한 1~2컷 시트 후보 생성 → 사용자 선택 → 컷별 크기·정렬·간격을 정한 세로 편집 → 승인본 보관** 순서로 진행합니다.

공개 `validate_project.py`의 page ID 잠금 형식이 새 컷 시트 프로필이나 세로 편집·업로드 분할 단계를 자동으로 검증해 주지는 않습니다. 또한 특정 작품에서 쓴 `1024x1536` 크기, 컷 수, 고정 중앙 흰띠 폭, 인물 수 상한, 의상, 배율과 간격을 모든 작품의 공통 규칙으로 복사하지 않습니다.

## 2. 고정 캐릭터는 먼저 레퍼런스를 준비한다

반복 등장하는 캐릭터는 이름과 텍스트 묘사만으로 고정하지 않습니다. 최소한 아래 기준 이미지를 사용자가 직접 눈으로 보고 승인해야 합니다.

### 최소 팩

1. `identity_primary` — 정면 또는 3/4 시점에서 얼굴, 머리, 체형, 핵심 의상이 명확한 무텍스트 기준 이미지.
2. 가능하면 `turnaround` — 앞·옆·뒤 또는 전신 비율을 보여주는 시트.
3. 가능하면 `expression_detail` — 표정과 제스처 범위를 보여주는 보조 시트.

무텍스트 이미지를 권장하는 이유는 레퍼런스 안의 글자, 말풍선, UI, 다른 인물이 다음 생성에 끼어들어 화면을 오염시키기 쉽기 때문입니다.

### 좋은 identity reference 조건

- 캐릭터 한 명이 명확하게 보입니다.
- 얼굴, 헤어, 체형, 의상 색, 실루엣을 한눈에 판별할 수 있습니다.
- 다른 캐릭터, 대사, 로고, 복잡한 배경이 최소화되어 있습니다.
- 극적인 패널 연출보다 “이 캐릭터가 누구인가”를 보여주는 이미지입니다.
- 사용자가 직접 확인하고 정본으로 승인했습니다.

### 매핑 절차

1. 캐릭터에 안정적인 `role_id`를 부여합니다. 예: `CHAR_GEM_01`.
2. 파일에 `reference_id`를 부여합니다. 예: `REF_GEM_IDENTITY_V1`.
3. `04_locks/reference_manifest.csv`에 역할, 경로, ref 역할을 기록합니다.
4. SHA-256을 계산해 기록합니다.
5. 사용자가 파일을 직접 보고 맞는 역할인지 확인한 뒤 `visual_role_verified=true`로 바꿉니다.
6. 등장 페이지의 `page_cast_lock.csv`에서 `role_id`와 `reference_id`를 연결합니다.
7. 서로 다른 캐릭터가 같은 SHA-256을 가리키면 생성을 멈추고 매핑부터 바로잡습니다.

예시:

```csv
reference_id,role_id,ref_role,ref_path,sha256,visual_role_verified,notes
REF_GEM_IDENTITY_V1,CHAR_GEM_01,identity_primary,assets/characters/gem_identity_v1.png,ABC123...,true,user approved
```

이 공개 저장소는 개인 이미지·캐릭터 시트 원본·비공개 대화·긴 실행 로그를 포함하지 않으므로 `assets/characters/`는 각 사용자가 로컬에서 직접 준비합니다. 이미지 파일을 공개 Git에 올리지 않고 로컬 경로와 SHA-256 해시만 프로젝트 매니페스트에 기록해 관리할 수 있습니다.

## 3. 캐릭터 시트와 연속 장면 레퍼런스는 역할이 다르다

- `identity reference`: 캐릭터가 누구인지 고정합니다.
- `turnaround/expression reference`: 체형 비율과 연기 범위를 보조합니다.
- `style reference`: 선, 채색, 질감만 안내합니다.
- `scene-continuity reference`: 직전 장면의 무대, 군중, 카메라, 배치를 이어갑니다.

직전 패널만 붙이고 identity reference를 빼면 캐릭터 얼굴과 복장이 서서히 변합니다. 반대로 캐릭터 시트만 붙이고 continuity reference를 빼면 같은 장소가 매번 새로 그려집니다. 연속 장면에서는 두 종류를 함께 씁니다.

다만 단순히 `다음 페이지`나 `다음 컷`이라는 이유만으로 continuity reference를 붙이지는 않습니다. 생성 계획에서 먼저 장면 관계를 잠급니다.

- `independent_page`: 대화·정보·리액션의 다음 비트이지만 샷과 물리적 무대 상태는 새로 구성해도 되는 관계.
- `same_scene_continuation`: 같은 장소·시간·배치·행동이 실제로 이어지는 관계.
- `reused_shot_variation`: 같은 샷을 유지한 채 표정·소품·부분 동작만 변형하는 관계.

독립 장면에는 identity reference만 사용합니다. 나머지 두 관계에는 identity reference를 유지하면서 scene reference를 함께 붙입니다. 작법 퇴고(`docs/CRAFT_REVIEW.md`) 단계에서 장면 이해에 꼭 필요한 발화자·상대·반응·핵심 볼거리는 살리되 불필요한 구경꾼이나 반복 배경을 줄여 두면 연속성 유지 부담도 함께 줄어듭니다.

## 4. 커뮤니티 소스도 사용자가 기준을 준다

에이전트가 웹을 검색할 수 있어도 무엇이 특갤 독자에게 재미있게 읽힐지는 자동으로 결정되지 않습니다. 최소한 다음 기준은 사용자가 직접 주거나 승인해야 합니다.

- 핵심 anchor 글 또는 사건.
- 사실로 유지해야 할 내용(`primary_fact`).
- 커뮤니티에서 실제로 관측된 말투·댓글·밈(`mood_source`).
- 사용자가 넣고 싶은 해석이나 풍자 방향.
- 과장 가능한 `MSG`와 건드리면 안 되는 선(`do_not_use`).

실시간 주제는 표본을 좁고 선명하게 잡습니다. 오래된 인기글을 넓게 섞으면 지금 다루는 사건의 고유한 결이 사라지고 흔한 커뮤니티 클리셰로 평준화됩니다.

## 5. 콘티와 작법 퇴고는 자료 요약과 다르다

에이전트가 자료를 빠짐없이 요약했다고 해서 곧바로 이미지 생성으로 넘어가면 만화가 아니라 카드뉴스가 됩니다. 작법 퇴고(`docs/CRAFT_REVIEW.md`)는 반드시 **전편(작품 전체의 감정·인과·보상) → 장면 연결 → 컷 설계** 순서로 진행합니다. 자료를 첨부하고 스크립트 기술 검사를 통과(`PASS`)한 것은 실제 퇴고가 아닙니다.

모든 컷은 다음 네 질문에 답해야 합니다.

1. 이전 컷에서 왜 넘어오는가(`handoff_from_previous`).
2. 독자가 먼저 무엇을 보는가(`reader_first_sees`).
3. 인물이 방금 무엇을 알거나 오해하는가(`character_realizes`).
4. 그래서 다음 컷이 왜 발생하는가(`push_to_next`).

이 네 칸 중 하나라도 비어 있으면 아직 콘티가 아니라 자료 배치입니다. 무엇을 왜 유지하거나 고쳤는지는 기존 콘티 메모에 남기면 충분하며, 매 컷마다 별도의 보고서나 승인 절차를 새로 만들 필요는 없습니다.

### 역할 분담과 공개 검증기 계약

제작 과정에서 각 주체의 역할은 분명히 나뉩니다.

- **사용자**: 작품의 의미·취향·각색 방향 결정과 최종 시각·원고 선택
- **AGY(Gemini)**: 위임받은 집필과 문장·대사·콘티 편집(거친 뼈대의 빈칸 채우기뿐 아니라 자유 집필, 완성문 퇴고도 실제 위임 범위에 따라 수행)
- **Codex**: 사실·연속성 확인과 파일·스크립트·생성 실행

GPT/Codex가 소스와 필수 필드를 잘 채우더라도 스스로 쓴 초안의 말맛, 개그 타이밍, 독자 보상까지 자체 보증할 수는 없습니다. 특히 공개 키트의 `validate_project.py`는 다음 콘티 이력과 해시 잠금을 요구합니다.

1. 최초 초안 또는 거친 장면 뼈대를 `v1`로 보존합니다.
2. Gemini(AGY)가 같은 소스 근거와 `v1`을 바탕으로 집필·검수 의견과 콘티 `v2`를 작성하고, 그 원출력을 보존합니다.
3. 사용자는 `v1`, Gemini 원출력, `v2`를 비교해 채택·각색·반려를 결정하고 필요하면 `v3`로 수정합니다.
4. 사용자가 최종 승인한 버전만 `current_version`으로 기록합니다.
5. `04_locks/editorial_review_lock.csv`에 Gemini와 human 두 행을 모두 남기고 각 근거 파일의 SHA-256을 기록합니다.

Gemini를 호출할 수 없는 환경에서 다른 에이전트가 이 단계를 임의로 GPT 자기검수로 대체하면 안 됩니다. 사용자에게 공개 검증기 기준 워크플로를 완수할 수 없다고 알리고, Gemini 원출력과 사람 승인이 준비될 때까지 본생성으로 넘어가지 않습니다.

## 6. 화면 글자는 내용·소유자·모바일 가독성을 함께 잠근다

대사 목록만 던져 주면 이미지 모델은 누가 말하는지 임의로 추측합니다. 화면에 들어갈 모든 렌더 텍스트에는 다음 정보를 기록합니다.

- `text_id`
- 실제 렌더할 문구
- `user-approved MSG`, `gallery phrase`, `source-function adaptation`, `SFX/prop/title` 중 source class
- `text_owner`
- `owner_role`: speech, thought, caption, sign, SFX, prop, comment 등
- `attachment_hint`: 말풍선 꼬리 대상, 댓글 카드, 표지판 내부 등
- `read_order`

`needs user approval` 상태인 문구가 하나라도 남아 있으면 글자가 포함된 본생성을 시작하지 않습니다.

또한 최종 독자는 스마트폰 화면의 표시 폭과 축소 상태에서 만화를 읽습니다. 따라서 생성 프롬프트 본문에도 글자 크기, 대비, 말풍선 여유 공간을 확보해야 하는 이유(WHY)를 함께 적어 전달합니다(`docs/CUT_BASED_PRODUCTION.md`). 이미 생성된 컷에서 기존 글자를 그대로 유지하기로 한 사용자의 결정은 그대로 보존하며, 데스크톱 화면에서 축소해 보는 것과 실제 스마트폰 기기에서 읽히는 감각은 다르다는 점을 염두에 둡니다.

## 7. 이미지 생성 전에 사용자가 승인해야 하는 것

현재 키트의 기본 이미지 생성 실행기는 별도 설치하는 `ima2-gen`입니다. 실제 생성 전에 Node.js 20+와 `ima2-gen`의 CLI/server가 정상 동작하는지 확인하고, `generation_plan.csv`의 `runtime`에 `ima2-gen`을 기록합니다. 다른 실행기를 쓴다면 실제 실행기 이름을 기록하되 같은 입력·증거 계약을 지킵니다.

생성 전 최소 승인 목록:

- 주제와 해석, 스윗스팟
- 캐릭터 스탠스와 등장 범위
- 전편→장면→컷 순서로 퇴고된 인과 콘티
- AGY(Gemini) 원출력과 사람이 최종 승인한 콘티 버전
- 렌더할 문구와 화자 귀속
- 고정 캐릭터 정본 레퍼런스(`visual_role_verified=true`)
- 승인한 생성 수량·비용 범위 및 첫 파일럿 확인 대상

에이전트가 출력한 기술적 `PASS` 보고서는 사용자의 창작 승인을 대신하지 않습니다.

## 8. 파일럿 확인과 후보 선택에서 볼 것

파일럿은 처음 실행기를 도입하거나 프롬프트·입력 구조를 바꿨을 때 그 내용이 실제 provider까지 깨지지 않고 전달되는지 확인하는 절차입니다. 매번 작은 배치만 생성하라고 강제하는 규칙이 아닙니다. 파일럿 확인이 끝나면 사용자가 승인한 장수·비용 안에서 단위 시간당 고를 만한 후보 수를 확보하는 방향으로 생성합니다.

에이전트의 객관 확인:

- 올바른 prompt 전문과 reference가 실제 provider에 전달됐는가.
- 한국어가 전송 과정이나 로그에서 `?`로 깨지지 않았는가.
- 파일이 생성됐고 바이트 크기·경로·요청 식별자가 기록됐는가.
- 프롬프트 안에 작품 맥락, 장면 전후 상태, 정확한 대사, 화면 계약이 빠짐없이 들어 있는가.

사용자의 시각 확인:

- 캐릭터가 정본처럼 느껴지는가.
- 표정과 장면의 말맛, 호흡이 살아 있는가.
- 1~2컷 시트라면 컷 분리가 가능하고, 전체 페이지라면 흰 여백과 그림 블록의 리듬이 맞는가.
- 스마트폰 표시 폭 기준으로 말풍선과 UI 글자가 선명하게 읽히는가.
- 후보 중 어떤 컷을 채택해 세로 편집(`docs/CUT_BASED_PRODUCTION.md`)과 업로드 분할(`docs/UPLOAD_DELIVERY.md`)로 넘길 것인가.

## 9. 다른 에이전트용 실행 지시문

저장소를 연결하거나 첨부한 뒤 아래 지시문을 에이전트에게 그대로 전달할 수 있습니다.

```text
AGENTS.md, docs/BEFORE_YOU_START.md, docs/QUALITY_CONTRACT.md,
docs/CUT_BASED_PRODUCTION.md, docs/CRAFT_REVIEW.md, docs/UPLOAD_DELIVERY.md,
skills/community-webtoon-producer/SKILL.md를 먼저 끝까지 읽어라.

내가 주는 소스와 캐릭터 레퍼런스를 먼저 점검하고, 반복 캐릭터의 role_id,
reference_id, ref_role, SHA-256, visual_role_verified 상태를 매핑하라.
레퍼런스가 없거나 사용자 승인이 없으면 캐릭터 일관성을 보장한다고 말하지 말고 멈춰라.

source ledger -> sweet spot 승인 -> 전편·장면·컷 작법 퇴고와 인과 콘티 ->
Gemini(AGY) 집필·검수 원출력 보존 -> 사람의 콘티 수정/최종 승인 ->
text/cast/reference locks -> provider prompt -> strict pre-generation validation 순서로 진행하라.
GPT/Codex의 자체 콘티 검사는 프론트 창작 품질 보증이 아니며 Gemini와 사람 검수를 대체할 수 없다.
내가 명시적으로 생성 범위와 수량을 승인하기 전에는 이미지를 생성하지 마라.
생성 후에는 후보를 임의 선별하지 말고 내가 직접 고를 수 있게 전달하라.
```

## 10. 같은 결과를 보장할 수 없는 경우

- 고정 캐릭터 레퍼런스 없이 이름과 설명만으로 반복 생성을 요구하는 경우.
- 실제 커뮤니티 소스 없이 “그럴듯한 특갤 분위기”만 만들어 달라는 경우.
- 사용자 방향 승인 없이 에이전트가 알아서 스윗스팟을 정한 경우.
- 전편→장면→컷 퇴고와 인과 콘티 없이 바로 생성 프롬프트를 뽑은 경우.
- 생성용 1~2컷 시트의 내부 배치와 최종 세로 스크롤 편집 배치를 구분하지 않은 경우.
- 긴 한국어 문장을 가독성 설계나 후속 식자 대책 없이 이미지 모델에만 맡기는 경우.
- 첫 전달 확인 없이 변경된 입력을 대량 생성으로 바로 확대하거나, 데스크톱 축소 확인만으로 모바일 가독성을 단정한 경우.
- 이전 반려본과 현재 정본을 같은 후보·레퍼런스 폴더에 섞어 오염시킨 경우.

이런 상황이 보이면 에이전트는 결과를 과장해 보장하지 말고, 빠진 준비 단계부터 사용자와 함께 복구해야 합니다.
