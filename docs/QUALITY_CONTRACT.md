# Quality Contract

이 키트가 재현하려는 것은 특정 그림체가 아니라, 특갤툰의 말맛과 읽히는 호흡을 안정적으로 만들어 내는 제작 의사결정 구조다.

공개 저장소(`Q0916/community-webtoon-agent-kit`)는 이전 세대 작품을 재현하는 **기존 전체 페이지 프로필**과 최신 **컷 시트 생성 후 세로 편집 프로필**(`docs/CUT_BASED_PRODUCTION.md`, `docs/CRAFT_REVIEW.md`, `docs/UPLOAD_DELIVERY.md`)을 함께 다룬다. 아래 원칙은 두 방식 모두에서 흔들리지 않아야 하는 공통 계약이며, 프로필별 규칙이 다른 지점은 합치지 않고 명확히 구별한다.

## 0. 이해 일치가 미시 프롬프트보다 먼저다

정확하고 세밀한 수행 지시만으로는 만화의 재미와 설득력을 재현할 수 없다. 작품 전체의 이야기, 독자가 따라가야 할 감정 순서, 장면이 존재하는 이유, 핵심 모티브, `fact`와 `MSG`의 경계, 사용자가 짚어낸 미묘한 어긋남처럼 당장의 그리기 명령에는 부수적으로 보이는 맥락이 실제 장면 선택과 캐릭터 연기를 바꾼다.

이 원칙은 추상적인 작업 철학이 아니라 실제 시행착오에서 확인된 품질 결정 요인이다. 최신 제작 흐름 역시 **작품과 의도 이해 → 전편의 감정·인과·보상 퇴고 → 장면 연결 → 컷 설계 → 전체 흐름/현재 구간/앞뒤 상태/정확한 대사/WHY를 담은 실제 입력** 순서로 움직인다. 작업을 분업할 때마다 다음 단계가 판단 근거를 복원할 수 있도록 충분한 맥락을 함께 넘긴다. 파일 경로·해시·레퍼런스·직전 출력은 provenance와 화면 상태를 증명할 뿐, 작품의 의미를 대신 전달해 주지 않는다.

프롬프트 분량을 줄여야 할 때는 중복된 수행 지시나 뒤쪽 부록부터 줄인다. 작품 전체의 이유와 감정선은 `soft context`라는 이유로 삭제하지 않는다.

## 1. 소스 진실과 개그 MSG를 분리한다

소스 원장(source ledger)은 최소 네 종류로 구분한다.

- `primary_fact`: 실제 사건과 원문 주장.
- `mood_source`: 커뮤니티에서 실제 관측된 반응, 말투, 밈의 태도.
- `MSG`: 재미를 위해 창작하거나 과장한 연결과 대사.
- `do_not_use`: 오래됐거나 반박됐거나 현재 주제와 무관한 자료.

커뮤니티에서 실제로 관측되지 않은 분위기를 대표 여론처럼 꾸며 쓰지 않는다. 창작 대사와 과장 연출은 적극 쓰되 반드시 `MSG`로 구분해 기록한다.

## 2. 스윗스팟을 승인받는다

콘티에 들어가기 전에 세 가지 축을 한 문장으로 포갠다.

1. Director(사용자)가 보여주고 싶은 핵심 주장과 감정.
2. 해당 커뮤니티 독자가 기대하는 말맛과 장면.
3. 만화로서 보여줘야 할 시각적 보상: 그림·연기·선·구도·여백과 독자가 스스로 채우는 생략이 주는 직관적 쾌감.

이 합의가 없으면 자료 요약은 가능해도 만화의 방향은 잠글 수 없다.

## 3. 정보 배열을 인과 콘티로 바꾸고 전편→장면→컷 순서로 퇴고한다

작법 퇴고(`docs/CRAFT_REVIEW.md`)는 **전편(작품 전체의 감정·인과·보상) → 장면 연결 → 컷 설계** 순서로 진행한다. 참고 자료를 첨부하고 스크립트 기술 검사를 통과(`PASS`)한 것은 실제 퇴고가 아니다.

모든 컷은 다음 네 질문에 답해야 한다.

- `handoff_from_previous`: 왜 지금 이 컷으로 넘어오는가?
- `reader_first_sees`: 독자가 가장 먼저 보는 것은 무엇인가?
- `character_realizes`: 인물은 방금 무엇을 알거나 오해하는가?
- `push_to_next`: 그래서 왜 다음 행동이나 반응이 생기는가?

장면 이해에 꼭 필요한 발화자·상대·반응·핵심 볼거리는 보존하면서, 시선을 분산시키는 불필요한 구경꾼·반복 배경·연속성 부담을 덜어낸다. 이때 인물 숫자 자체를 기계적으로 최소화하는 것이 목적이 아니라 장면의 초점을 살리는 것이 목적이다. 무엇을 왜 유지하거나 고쳤는지는 기존 콘티 메모에 남기면 되며, 매 컷마다 새 보고서나 승인 절차를 추가하지 않는다.

결말 역시 작품이 목표로 하는 독자 경험에 맞춘다. 앞선 질문이나 농담을 회수할 수도 있고, 열린 가능성과 일상의 여운을 남길 수도 있다. 그 기능과 이유를 다음 단계 작성자에게 분명히 전달한다.

## 3A. 사용자·AGY·Codex의 역할 분담과 콘티 확정

실제 제작에서 세 주체의 역할은 다음과 같이 나뉜다.

- **사용자(Director)**: 의미·취향·각색 방향 결정과 최종 선택.
- **AGY(Gemini)**: 위임받은 집필과 문장·콘티 편집. 거친 뼈대의 빈칸 채우기뿐 아니라 자유 집필, 완성문 퇴고도 사용자의 실제 위임에 따라 수행한다.
- **Codex**: 사실·연속성 확인과 파일 정리·검증·생성 실행.

자료 해석, 장면 선택, 말맛, 타이밍, 펀치라인은 프론트 창작 작업이다. GPT/Codex는 구조 누락과 소스 불일치를 점검할 수 있지만, 자신이 쓴 콘티의 창작 품질을 스스로 보증할 수는 없다.

공개 키트의 `validate_project.py`가 요구하는 콘티 확정 및 잠금 경로는 다음과 같다.

1. 초기 장면 뼈대 또는 초안을 별도 파일(`v1`)로 보존한다.
2. Gemini(AGY)가 전체 소스 근거와 `fact`/`MSG` 경계를 읽고 집필·검수한 결과(`v2`)를 만들며, 그 원출력을 그대로 보존한다.
3. 사용자에게 AGY 원문을 먼저 그대로 보여주고, 제안을 `adopt`, `adapt`, `reject`로 함께 정리한다. 사실·연속성 정정도 합의된 범위 안에서 반영한다.
4. 합의된 결과만 하나의 canonical 콘티로 통합하고 사람이 최종 승인한다.
5. 사람 승인 canonical 버전만 이미지 생성용 패킷과 프롬프트의 기준선으로 삼는다.
6. 각 단계의 파일과 버전, SHA-256 해시를 `04_locks/editorial_review_lock.csv`에 기록한다. 초안 확정 후 편집·배치·제작 준비는 Codex가 이어받으며, AGY는 새 사용자 요청이 있을 때 다시 참여한다.

Gemini 원출력 보존과 사람의 최종 승인 해시가 빠지면 구조 검사를 통과하더라도 공개 키트의 검증 계약 범위 밖이다. 과거 사례의 raw 파일과 역사적 대화 기록은 당시 이력 그대로 보존하며 재작성하지 않는다.

## 4. 텍스트 내용·배치와 모바일 가독성을 함께 잠근다

Source lock은 “무슨 글자를 써도 되는가”를 증명하고, Routing lock은 “그 글자가 누구에게 어디로 붙는가”를 증명한다. 둘 중 하나만 있으면 말풍선 꼬리, 소품 글자, 댓글 카드, 화자 귀속이 흔들린다.

후보 생성에서는 기능적 위치를 지시하되 픽셀 좌표를 억지로 강제하지 않는다. 동시에 독자가 스마트폰 최종 표시 폭과 축소 화면에서 글자를 또렷이 읽을 수 있도록, 생성 프롬프트 본문에도 글자 크기·대비·말풍선 공간 확보의 목적(WHY)을 전달한다. 기존 생성 컷의 글자를 유지하기로 한 사용자 결정은 보존하며, 긴 정확 문장이 필요할 때는 후속 식자를 함께 활용한다. 데스크톱 축소 확인과 실제 스마트폰 기기 확인은 서로 다른 단계로 취급한다.

## 5. 캐스트와 레퍼런스를 데이터로 다룬다

화면에 보이는 인물마다 역할 ID(`role_id`)를 둔다. 반복 캐릭터는 파일 경로, 역할, SHA-256, 사람의 `visual_role_verified` 상태를 기록한다. 서로 다른 역할이 같은 해시를 가리키면 생성 전에 멈춘다.

장면 관계는 생성 전에 `independent_page`, `same_scene_continuation`, `reused_shot_variation` 중 하나로 선언한다. 이야기와 대사가 이어진다는 사실만으로 곧바로 visual continuity가 성립하지는 않는다. 연속 장면에서는 캐릭터 시트와 별도로 직전 승인 컷/페이지를 scene-continuity reference로 붙인다. 스킬/프로듀서가 관계를 판단하고, 하네스는 선언된 값과 프롬프트의 scene reference 일치 여부를 검사하며, provider runtime은 이를 임의로 재해석하지 않는다.

## 6. 화면에 실제로 보일 것만 작화에 적고 소품의 이유는 맥락으로 전달한다

현재 검증된 기본 이미지 생성 실행기는 별도 설치하는 `ima2-gen`이다. 스킬이 이야기와 장면 의미를 판단하고, 하네스가 승인·잠금·입력 일치를 검사하며, `ima2-gen`은 실제 생성 요청을 실행한다. `generation_plan.csv`에는 실제 사용한 `runtime` 이름을 기록한다.

provider prompt는 다음을 positive inventory로 명시한다.

- 정확한 visible cast
- 화면에 실제로 보일 오브젝트와 정보 소품의 면·문자
- 렌더할 텍스트 행과 소유자, 가독성·대비·말풍선 공간의 목적
- background budget
- 그림 블록 또는 컷 시트의 경계
- 자세, 실루엣, 색, 카메라, 읽기 순서

화면에 직접 보이지 않는 소품의 뒷면이나 설정을 작화 묘사에 우겨넣지 않되, 그 소품이 이야기에 등장하는 이유(WHY)는 전체 맥락으로 전달한다. 반려 사유·보험 문구·제작 주의사항은 내부 audit에만 두고 생성 입력에 첨부하지 않는다. 승인된 생성지침의 문맥·WHY·예시는 그대로 전달하며, 부정형 문구 분리 요청을 주변 설명까지 축약하라는 권한으로 확대 해석하지 않는다.

## 7. 전체 페이지 프로필과 컷 시트·세로 편집 프로필을 구별한다

이 저장소는 두 가지 화면 설계 프로필을 합치지 않고 구별한다.

### A. 기존 전체 페이지 프로필 (이전 세대 사례 재현 범위)
- 흰 세로 원고지를 출발점으로 삼고 `PANEL_LAYOUT_REVISION.md`에 따라 페이지 안의 컷 점유·크기·위치·식자·여백·경계를 설계한다.
- 초기 2-4블록 구성, 28-42% 여백, 60%/78% 표현 예산 가설 등은 해당 전체 페이지 프로필 작품(9월 12일 수학자툰, Amazon × OpenAI 사례 등)의 재현 지침으로 보존한다.
- 공개 `validate_project.py`는 이 page ID 기반 잠금 구조를 직접 검증한다.

### B. 최신 컷 시트 생성 및 세로 스크롤 편집 프로필 (`docs/CUT_BASED_PRODUCTION.md`)
- 분리 가능한 1-2컷 시트 후보를 생성해 사용자가 선택한 뒤, 컷별 크기·정렬·간격을 정해 최종 세로 원고로 편집한다(2026-10-17 꾸준툰 새로쓰기 65컷, 2026-10-21 미소녀툰 21컷 사례).
- **생성 시트 내부의 배치**와 **최종 세로 스크롤 배치**는 서로 다른 단계다. 특정 작품의 `1024x1536` 크기, 컷 수, 고정 중앙 흰띠 폭, 인물 수 상한, 의상, 배율과 간격을 모든 작품의 고정 규칙으로 복사하지 않는다.
- 세로 편집에서 컷 사이 실제 거리는 `앞 컷 아래 흰 여백 + 추가 간격 + 다음 컷 위 흰 여백`의 합이다. 목표 거리에서 부족한 만큼만 추가 간격을 더하며, 응답·반응·공개·침묵·진짜 장면 전환의 호흡을 구별한다.
- 공개 키트 자체에는 컷 시트 분리·재배치 도구가 포함되지 않으므로 사용자가 별도 편집 환경을 준비해 진행한다.

## 8. 파일럿 확인과 후보 풀 탐색을 구별한다

파일럿은 첫 실행기 도입이나 입력·프롬프트 변경이 실제 provider까지 정상 전달되는지(한국어, 레퍼런스, 화면 계약) 확인하는 절차이지, 매번 작은 배치만 생성하라는 제약이 아니다. 전달 확인이 끝나면 사용자가 승인한 장수·비용 안에서 단위 시간당 사람이 고를 만한 후보 수를 확보하도록 병렬 탐색을 운영하며, 최종 시각 선택은 사용자가 직접 맡는다.

## 9. 상태 표면을 깨끗하게 유지한다

현재 후보, 선택본, 반려본, 레거시를 폴더와 매니페스트에서 엄격히 분리한다. 구버전이 current나 prompt queue에 남아 다음 생성의 참고물로 섞이는 것이 반복 오염의 가장 큰 원인이다.

## 10. 최종 승인 동결과 업로드 분할 전달을 구별한다

작품 완성 보관은 다음 세 묶음을 해시로 동결할 때 끝난다.

- 게시·열람용 완성본(전체 보기 마스터 및 전달본)
- 사용자가 최종 승인한 개별 원본(페이지 또는 선택 컷)
- 실제 사용한 소스, 레퍼런스, 콘티, 프롬프트, 선택 기록

나머지 작업 이력은 legacy로 분리하되 자동 삭제하지 않는다.

이때 공개 키트의 `freeze_completion.py`는 파일 복사와 SHA-256 일치 검증을 수행하는 도구다. 디시인사이드 업로드용 기준(2026-10-21 실제 본문 이미지 축소 관측 뒤 사용자가 채택한 제작 기준인 **파일당 20,000,000바이트 미만, 세로 9,000px 이하** — 디시의 공식 한도나 모든 게시글의 서버 동작이 아님)에 맞춰 안전한 흰 여백에서 원본 폭·픽셀·행·글자·기존 여백을 보존해 무손실 분할하고 번호순으로 전달하는 작업(`docs/UPLOAD_DELIVERY.md`)은 `freeze_completion.py`가 자동 대행하지 않으므로, 사용자가 별도 편집·검사 도구를 준비해 수행한다.
